# EPI-ClimaNuvem — Playwright + C# Test Suite

Playwright (.NET) + NUnit test suite for [EPI-ClimaNuvem](https://gitlab.com/HP-SCDS/Observatorio/2025-2026/climanuvem/epi-climanuvem),
covering the same scenarios as the [`selenium-java`](../selenium-java) suite in this repository, translated to
idiomatic Playwright/.NET rather than ported line-for-line.

Covers two test layers:
- **API tests** (`Tests/Api/`) — HTTP-level tests against the FastAPI backend via `HttpClient` (no browser needed)
- **System tests** (`Tests/E2e/`) — Playwright-driven tests against the Expo web frontend, using a Page Object Model

## Quick start

### 1 — Deploy the SUT in test mode

`sut/docker-compose.test.yml` (shared by every test suite in this repo — not duplicated per-suite) builds the
backend and frontend from `sut/backend` and `sut/frontend` and starts them with `TEST_MODE=true` — no Firebase
project or Ollama needed for the default suite.

```bash
docker compose -f ../sut/docker-compose.test.yml up --build -d
```

Services started:

| Service | URL |
|---|---|
| Backend (FastAPI) | http://localhost:8000 |
| Frontend (Expo web) | http://localhost:5173 |

### 2 — Restore dependencies and install the Playwright browser

```bash
dotnet build
pwsh bin/Debug/net8.0/playwright.ps1 install chromium
```

(`playwright.ps1` is generated by the `Microsoft.Playwright` build target — it only exists after the first
`dotnet build`. Requires PowerShell; on Linux/macOS CI that means `pwsh`, the cross-platform PowerShell, not a
Windows-only dependency.)

### 3 — Run the tests

```bash
dotnet test                                                          # everything (API + system)
dotnet test --filter "FullyQualifiedName~Tests.Api"                   # API tests only
dotnet test --filter "FullyQualifiedName~Tests.E2e"                    # system tests only (drives Chromium)

dotnet test --filter "FullyQualifiedName~LoginSystemTests"
dotnet test --filter "FullyQualifiedName~RegisterSystemTests"
dotnet test --filter "FullyQualifiedName~ProfileSystemTests"

CI=true dotnet test --filter "FullyQualifiedName~Tests.E2e"            # headless Chromium (for CI or no display)
```

### Real image-analysis tests with Ollama

The default deployment starts the backend with `DISABLE_WORKER=true`, so `dotnet test` skips the real
image-analysis suite and does not require Ollama. To exercise the full image-analysis flow, layer the optional
Ollama compose file on top:

```bash
docker compose -f ../sut/docker-compose.test.yml -f ../sut/docker-compose.ollama-test.yml up --build -d
```

Then run only the real image-analysis suite:

```bash
REAL_OLLAMA_TESTS=true dotnet test --filter "FullyQualifiedName~ImageAnalysisSystemTests"
```

`REAL_OLLAMA_TESTS=true` enables the analysis worker, starts an Ollama container, and pulls
`${OLLAMA_MODEL:-gemma4:e4b}`. The first run can take longer while the model downloads. These tests validate the
real upload and processing flow: image upload, history polling, cloud detection, explainability boxes, no-cloud
images, and file validation cases. Without `REAL_OLLAMA_TESTS=true`, every test in this fixture reports as
**skipped** (`Assert.Ignore`), not run.

### 4 — Tear down

```bash
docker compose -f ../sut/docker-compose.test.yml -f ../sut/docker-compose.ollama-test.yml down --volumes
```

(Omit `-f ../sut/docker-compose.ollama-test.yml` if you never started it; `--volumes` removes the Postgres and
Ollama data volumes for a clean next run.)

## Configuration

Account data for the system suite is loaded from a CSV file instead of individual email/password variables,
exactly like `selenium-java`.

Create your local account file from the template:

```bash
cp Resources/accounts.template.csv Resources/accounts.local.csv
```

`accounts.local.csv` is ignored by Git and should contain the real accounts used by local or CI runs:

```csv
role,email,password,verified,description
login_user,user@example.com,secret,true,Existing account for login tests
profile_user,verified-user@example.com,secret,true,Verified account for profile tests
unknown_user,missing@example.test,wrong-password,false,Non-existing account for negative login tests
```

Roles:

- `login_user`: existing account used by `LoginSystemTests` and by the "email already in use" registration case.
- `profile_user`: verified account used by authenticated profile tests. May be the same account as `login_user`.
- `unknown_user`: account expected not to exist, used for negative login attempts.

`LoginSystemTests` and `ProfileSystemTests` use NUnit's `[TestCaseSource]` to iterate every row for
`login_user`/`profile_user` — the direct equivalent of JUnit's `@ParameterizedTest`/`@MethodSource`. Each case
gets its own NUnit test instance (visible individually in test results, e.g.
`AuthenticatedDeleteAccountShowsConfirmationAndCanBeCancelled(profile_user:verified-user@example.com)`) **and**
its own fresh incognito browser context, courtesy of `BrowserTestBase`'s `PageTest` base — matching
selenium-java's fresh-ChromeDriver-per-parameterized-row behavior with no extra plumbing needed.

All values below are plain environment variables, read by `Common/TestSettings.cs`:

| Variable | Default | Description |
|---|---|---|
| `SUT_URL` | `http://localhost:8000` | Backend base URL used by API tests |
| `FRONTEND_URL` | `http://localhost:5173` | Frontend base URL used by system tests |
| `TEST_TOKEN` | `test-token-climanuvem` | Auth token injected by API tests |
| `HTTP_TIMEOUT_MS` | `10000` | HTTP client timeout for API tests |
| `ANALYSIS_TIMEOUT_MS` | `360000` | Maximum wait for real image-analysis completion |
| `ACCOUNTS_FILE` | `Resources/accounts.local.csv` | CSV file with system-test accounts |
| `REGISTER_EMAIL_DOMAIN` | `gmail.com` | Domain used for unique registration-test emails |
| `FIREBASE_WEB_API_KEY` | _(unset)_ | Optional Firebase Web API key used to delete the account created by `RegisterSystemTests` |
| `REAL_OLLAMA_TESTS` | `false` | Set `true` to enable `ImageAnalysisSystemTests` |
| `CI` | _(unset)_ | Set to `true` for headless Chromium |

`RegisterSystemTests`'s account-creation test builds a unique email address from `REGISTER_EMAIL_DOMAIN` and
expects the email-verification guidance shown by the app. If `FIREBASE_WEB_API_KEY` is configured, the test
deletes that Firebase Auth account afterward; otherwise the unique address just prevents future test collisions.

## Test architecture

```
Common/
├── TestSettings.cs        Environment-driven settings (SUT_URL, FRONTEND_URL, TEST_TOKEN, ...)
├── ApiTestBase.cs           HTTP helpers, multipart upload, JSON parsing (System.Net.Http + System.Text.Json)
├── ApiResponse.cs            Status code + body pair, for tests that need both at once
├── TestImages.cs              JPEG fixture synthesis (SixLabors.ImageSharp — Apache-2.0-licensed 3.x line)
├── BrowserTestBase.cs        Playwright PageTest base + navigation entry points (mirrors BaseLoggedClass)
├── TestAccount.cs             Account row used by [TestCaseSource]-driven system tests
└── TestAccounts.cs             CSV loader and role lookup for system-test accounts

Pages/                       Page Object Model — one class per screen
├── BasePage.cs                Shared locator factories + poll-based wait/click/fill primitives
├── WelcomePage.cs
├── LoginPage.cs
├── RegisterPage.cs
├── HomePage.cs
├── CapturePage.cs
└── ProfilePage.cs

Tests/
├── Api/                       HTTP-level tests (no browser)
│   ├── PingTests.cs
│   ├── AuthTests.cs

│   ├── CancelTests.cs
│   ├── DeleteTests.cs
│   ├── HistoryTests.cs
│   └── ImageAnalysisSystemTests.cs

    ├── LoginSystemTests.cs

├── accounts.template.csv      Versioned example for system-test account data
└── accounts.local.csv          Local/CI account data, ignored by Git
```

Page objects navigate the same way `selenium-java`'s do — every action returns the next screen, just as an
awaited `Task<TPage>`:

```csharp
// No auth required
var welcome = await OnWelcomePageAsync();
var login = await welcome.ClickLoginButtonAsync();
var register = await login.ClickRegisterLinkAsync();

// Authenticated flow
var home = await LoginAsGuestAsync();          // Firebase anonymous auth
var capture = await home.ClickAnalyzeImageAsync();
var back = await home.ClickLogoutAsync();
```

### Why this isn't a line-for-line port

Playwright's own NUnit integration (`Microsoft.Playwright.NUnit.PageTest`, which `BrowserTestBase` extends)
already provisions a fresh, isolated `Page` (backed by a fresh `IBrowserContext`) for every test with zero
manual lifecycle code — Selenium's `--incognito` + fresh-`ChromeDriver`-per-`@BeforeEach` collapses into "extend
`PageTest`." `ElementHandle.ClickAsync()`/`FillAsync()` dispatch real-enough browser events that React Native
Web's handlers pick up natively, so the JS-dispatched-click and native-setter plumbing selenium-java's
`BasePage` needed for WebDriver is not reproduced here.

Several of our locators (submit buttons matched by role/tag *and* text, the duplicated "Sistema" option)
legitimately resolve to more than one element, which Playwright's strict-mode locator actions reject outright.
Every "wait until visible" and "click" in `BasePage` therefore routes through `VisibleMatchAsync` — a manual
poll (scan all current matches every 200ms, first-to-last or last-to-first) that is the direct translation of
selenium-java's `wait.until(webDriver -> {...})` loops, rather than relying on Playwright's single-match
`WaitForAsync`.

Where a single JUnit `@Test` used `Assertions.assertAll(...)` to bundle several *independent* checks
(login/register validation, theme/language selection), the direct NUnit equivalent — `Assert.Multiple(...)` —
is used here too, including its `AsyncTestDelegate` overload for assertions that need `await`. Account-row
parameterization uses `[TestCaseSource]`, NUnit's own equivalent of `@ParameterizedTest`/`@MethodSource` — no
`subTest`/`describe.skip`-style workaround needed, since it's a first-class, built-in mechanism here.

Multipart image upload uses `System.Net.Http.MultipartFormDataContent` directly — no extra library needed,
unlike the Cypress/Puppeteer ports which had to route around their HTTP client's limitations. JPEG fixture
synthesis uses `SixLabors.ImageSharp` **3.1.x** specifically: the 4.x line moved to a commercial license that
hard-fails the build without a paid key, so the `.csproj` pins the last Apache-2.0-licensed 3.x patch instead.

## Test mode

The backend is started with `TEST_MODE=true` and `DISABLE_WORKER=true` (see `../sut/docker-compose.test.yml`):

- **Any Bearer token** is accepted — API tests use a fixed token; system-test guest login uses real Firebase anonymous tokens.
- **Firebase is not initialised** — no service account key is needed.
- **Ollama worker is disabled** — analyses stay in `analyzing` state, making cancel tests deterministic.

The optional real image-analysis suite has its own Ollama deployment flow in the quick-start section above.
